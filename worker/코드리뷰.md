## 1. main.py: Kafka 입구와 출구

| 줄 | 내용 |
|---|---|
| 1~7 | (대충) 파일 설명. 받기 → 그래프 → 결과 보내기 → commit 4단계 |
| 9~18 | (대충) import. `aiokafka`가 Python용 Kafka 라이브러리, `C`는 config |
| 20 | 로그 이름표 |
| ★ 21 | `GRAPH = build_graph()`: 그래프를 프로그램 켤 때 한 번만 조립 |
| ⚠️ 22 | `done`: 처리한 명령 id 기록. **메모리라 껐다 켜면 사라진다** → 하네스 담당이 DB로 |

### make_emit (25~45): 결과 보내기 함수 만들기

| 줄 | 내용 |
|---|---|
| ★ 25 | 명령 하나마다 그 명령 전용 `emit` 함수를 만든다. 그래프 노드들이 이걸로 Spring에 알린다 |
| 30 | `seq = 0`: 이 명령에서 보낸 결과 개수 |
| 33~34 | 보낼 때마다 seq +1. `nonlocal` = 바깥 변수 seq를 고친다는 뜻 |
| ★ 36 | 명령에 있던 id 6개(repairId, taskId, executionId 등)를 결과에 **그대로 복사**. Spring이 이걸로 어느 작업 결과인지 찾는다 |
| ★ 37 | `eventId` = 명령 id + 번호로 만든 고정 UUID. 같은 결과를 두 번 보내도 id가 같아서 **Spring이 중복을 알아서 버린다** |
| 38~41 | 이벤트 종류, 시각, 번호, 내용 |
| ★ 43 | `diagnosis.events.v2`로 전송. **key = taskId** → 같은 작업 메시지는 순서가 지켜진다 |

### handle (48~65): 명령 하나 처리

| 줄 | 내용 |
|---|---|
| ★ 50 | emit을 재시도 바깥에서 한 번만 만든다. 재시도해도 번호가 이어진다 (1로 돌아가면 Spring이 무시) |
| 51 | "시작" 이벤트 |
| 52 | 최대 3번 시도 (`MAX_RETRY=2` + 1) |
| ★ 54 | **그래프 실행.** 입력은 명령 원문, `configurable.emit`으로 보내기 함수를 쥐여 준다 |
| 55 | 그래프가 만든 마지막 결과 꺼내기 |
| 56~57 | 사진 요청이면 `requestKey`(이 요청의 고유 id)를 붙인다. Spring이 사진 재제출 때 이 값을 돌려준다 |
| 58 | 마지막 결과 전송 (완료 / 사진요청 / 실패) |
| 61~63 | 에러 나면 로그 남기고 1초, 2초 쉬었다 재시도 |
| ⚠️ 54 | 재시도는 그래프를 **처음부터** 다시 돌린다 → 진행·도구 이벤트가 중복으로 쌓인다. 동작은 문제없음 |
| 64~65 | 3번 다 실패 → "실패" 이벤트 + 명령 원문을 DLT 토픽에 보관 |

### run (68~90): 메인 반복

| 줄 | 내용 |
|---|---|
| ★ 69~70 | consumer. `group_id=langgraph-diagnosis-v2`(Spring과 약속한 이름), **`enable_auto_commit=False`** = 우리가 다 처리한 뒤에만 "받았다" 기록 |
| 71 | producer. `acks="all"` = Kafka가 확실히 저장해야 성공 |
| 72~74 | (대충) 시작 + "대기 중" 로그. GPT 켜짐/꺼짐도 표시 |
| ★ 76 | `async for msg in consumer`: 메시지가 올 때마다 한 개씩 |
| 77~81 | JSON으로 읽고, 우리가 아는 명령(REQUESTED/RESUMED)인지 확인 |
| 82~83 | 모르는 것·깨진 것 → DLT |
| 84~86 | 처음 보는 명령이면 처리하고 `done`에 기록 |
| ★ 87 | **commit은 맨 마지막.** 처리 중에 죽으면 commit이 안 됐으니 다시 켜면 같은 명령을 또 받는다 |
| 88~96 | (대충) 종료 정리, 로그 설정, 실행 |
